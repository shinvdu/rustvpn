# Производительность

[English](../en/performance.md) | [中文](../zh/performance.md) | **Русский**

Эта страница объединяет записи об оптимизациях со стороны Go и сравнение Rust с Go на одной машине. Все числа — это микробенчмарки кодека пакетов (без TAP, без NIC), если не указано иное, и они зависят от общей/виртуализированной машины; сравнивайте только числа из одного пакета измерений.

## Окружение и методика

- CPU: AMD Ryzen 5 PRO 5675U (Zen3, AVX2), 12 потоков.
- Go 1.22.2 linux/amd64, `GO111MODULE=off GOPATH=$(pwd)`.
- Rust edition 2021, `cargo build --release`, диспетчеризация AVX2 во время выполнения.
- Go: `-count 5 -benchmem`; Rust: `crypto_bench` / `proto_bench` с внутренним считающим аллокатором. Результаты — медианы пяти прогонов.
- Входные данные согласованы с бенчмарками Go (`MTUDefault = 1515`): classic 789 B, noise MTU 1490 B, encless 128 B, encless MTU 1506 B, CnW 16 B, AONT 128 B.

```bash
# Go (требуется исходное дерево GoVPN 5.7; в этот репозиторий оно не входит)
cd /path/to/upstream-govpn
GO111MODULE=off GOPATH=$(pwd) go test -run XXX -bench . -benchmem -count 5 \
  cypherpunk.ru/govpn cypherpunk.ru/govpn/cnw cypherpunk.ru/govpn/aont

# Rust (из корня этого репозитория)
cargo build --release --examples
for i in 1 2 3 4 5; do ./target/release/examples/crypto_bench; done
for i in 1 2 3 4 5; do ./target/release/examples/proto_bench; done
```

## Оптимизации со стороны Go

Реализация на Go была оптимизирована первой — как для устранения реальных узких мест, так и для установления честной базовой линии. Байты на проводе не изменены.

| Изменение | Результат |
|---|---|
| CnW: формула Poly1305 для 1 байта + один HSalsa20 на пакет | Chaff **4.45×**, Winnow **6.72×** |
| Encless: удаление промежуточных срезов/копий | декодирование 128 B **5.49×**, декодирование MTU **5.44×**; выделения при декодировании 5 → 1 |
| Путь отправки peer'а: без `append` на каждый пакет, точечное обнуление | шифрование classic **1.54×**, дешифрование **1.13×**; выделения 1 → 0 |
| Проверка MTU для noise/encless | кадры превышающего размера отклоняются вместо молчаливого усечения |
| Путь данных UDP-сервера | без goroutine на каждый пакет, без лимита в 2 буфера на peer'а, без строк/глобальной блокировки на каждый пакет |
| Кэш идентичностей, параллелизм конфигурации/TAP | последовательное сканирование, снимки RWMutex, ошибки чтения TAP больше не вызывают panic |

До/после (медиана из 3):

| Сценарий | До | После | Выигрыш |
|---|---:|---:|---:|
| classic 789 B encrypt | 2,805 ns | 1,827 ns | 1.54× |
| classic 789 B decrypt | 2,068 ns | 1,827 ns | 1.13× |
| classic noise MTU encrypt | 4,217 ns / 359 MB/s | 3,040 ns / 490 MB/s | 1.39× |
| encless 128 B encode | 32,817 ns | 11,232 ns | 2.92× |
| encless 128 B decode | 54,688 ns | 9,964 ns | 5.49× |
| encless MTU encode | 42,288 ns / 35.8 MB/s | 15,326 ns / 98.3 MB/s | 2.76× |
| encless MTU decode | 75,593 ns / 20.0 MB/s | 13,889 ns / 108.8 MB/s | 5.44× |
| CnW Chaff (16 B) | 41,097 ns | 9,235 ns | 4.45× |
| CnW Winnow (16 B) | 58,928 ns | 8,769 ns | 6.72× |

Почему CnW важен: Winnow выполняет 512 вычислений Poly1305 по одному байту на пакет (256 одноразовых ключей × 2 кандидатных тега). Обычный вызов Poly1305 определяется разбором ключа и финализацией, поэтому оптимизированная форма вычисляет оба кандидатных тега для ключа **одним** 130-битным умножением:

```text
block("0") = 0x30 + 0x01 * 2^8 = 0x130
block("1") = 0x131

h0   = 0x130 * r  mod (2^130 - 5)
h1   = (h0 + r)   mod (2^130 - 5)
tag0 = low128(h0 + s)
tag1 = low128(h1 + s)
```

где `r` ограничивается согласно RFC 8439, а выбор/сравнение выполняются за постоянное время. Реализация на Rust использует ту же формулу и дополнительно пакетирует восемь независимых keystream'ов через AVX2.

## Решения в реализации на Rust

- `encode_into` / `decode_into` с переиспользуемыми буферами: classic/noise достигают **0 выделений памяти на пакет** на пути peer'а.
- AVX2 Salsa20 охватывает все полные 64-байтные блоки *и* финальный частичный блок; скалярный хвост удалён. CnW вызывает AVX2-ядро для 8 потоков пакетами по 8 байт.
- Poly1305 закреплён за программным бэкендом. На этой машине Zen3 бэкенд AVX2 этого крейта имеет фиксированную стоимость ~845 ns и в 2.5–4.5× медленнее скалярного бэкенда на диапазоне 16 B–1500 B.
- UDP использует `recvmmsg`/`sendmmsg` на 64 датаграммы; TAP использует io_uring с пробуждением через eventfd и запасной вариант на epoll.

| Сценарий | Go | Rust |
|---|---:|---:|
| classic 789 B encode | 401 MB/s | 603 MB/s |
| classic 789 B decode | 399 MB/s | 590 MB/s |
| noise MTU encode | 449 MB/s | 720 MB/s |

## Тайминги компонентов (classic 789 B, Rust)

| Компонент | Время | Примечание |
|---|---:|---|
| XTEA encrypt/decrypt 8 B | 76.0 / 73.9 ns | 64 раунда, предвычисленные таблицы |
| Salsa20 XOR 854 B | 574.7 ns | AVX2, все блоки + хвост |
| Salsa20 XOR 1500 B | 793.5 ns | AVX2 |
| Poly1305 tag 798 B (soft) | 590.7 ns | закреплённый бэкенд |
| Poly1305 tag 798 B (AVX2 path) | 1,523 ns | не используется |
| Poly1305 tag 16 B (soft / AVX2) | 24.8 / 845.1 ns | видна фиксированная стоимость AVX2 |

76 + 575 + 591 ≈ 1,242 ns плюс ~60 ns на копирование/фрейминг соответствует измеренным 1,308 ns.

## Оговорки

- Результаты получены на общей/виртуализированной машине; один прогон может варьироваться на ±20%. Разные пакеты измерений Go (ранние и поздние) отличаются на 10–15%, поэтому не смешивайте числа из разных документов.
- Пропускная способность пакетного ввода-вывода отсутствует в этой таблице: сквозной pps зависит от NIC, ядра и TAP-бэкенда, а тестовый хост не может создавать TAP без привилегий. Корректность путей пакетной обработки/io_uring покрыта тестами loopback/socketpair.
- Бенчмарка декодирования noise MTU для Go нет, поэтому в этой строке указан только Rust.
- Оставшиеся возможности: многопакетный SIMD Poly1305, кодирование encless с пулом буферов, битслайсинг XTEA по пакетам и timer wheel для очень большого числа peer'ов. Передача при отправке UDP на сервере стоит 1 выделение на пакет; пул мог бы её устранить (ожидается <100 ns/пакет).
