# Дизайн

[English](../en/design.md) | [中文](../zh/design.md) | **Русский**

Эта страница описывает реализованную архитектуру. Исходное предложение по дизайну сохранено в этом репозитории как [`docs/design.md`](../design.md) (написано до переименования, поэтому там ещё используются старые имена `govpn-*`); эта версия фиксирует то, что было действительно построено и почему.

## Цели

1. **Совместимость по проводному формату прежде всего.** Бинарники на Rust должны быть полноценной заменой GoVPN 5.7 (drop-in). Байты протокола, флаги CLI, значения по умолчанию, `peers.yaml`, скрипты, JSON статистики и поведение прокси — всё это часть поверхности совместимости.
2. **Вторая реализация как оракул.** Дифференциальное тестирование против кода на Go выявляет дрейф протокола, который одни только модульные тесты пропустили бы.
3. **Предсказуемый путь данных.** Никаких выделений памяти в куче на каждый пакет в установившемся режиме, ограниченные очереди, явное владение буферами и пакетный ввод-вывод.
4. **Операционный паритет.** Та же модель развёртывания, права доступа и диагностика, что и у демонов на Go.

Не-цели этой версии: протокол v2, Windows/macOS, GUI, управление маршрутизацией/NAT, управляющие плоскости балансировки нагрузки или изменение любого криптографического алгоритма (это нарушило бы совместимость).

## Структура воркспейса

```text
.
├── crates/rustvpn-crypto/   # primitives, AONT/CnW/encless, verifier, EGD
├── crates/rustvpn-proto/    # packet layout, codec, handshake state machines
├── crates/rustvpn-net/      # TAP, config, scripts, stats, peer lifecycle,
│                            # UDP batching, io_uring TAP
├── crates/rustvpn-client/   # client binary
├── crates/rustvpn-server/   # server binary
├── crates/rustvpn-verifier/ # verifier binary
├── testdata/                # Go-generated differential vectors
└── docs/                    # this manual (en/zh/ru) + upstream design notes
```

`rustvpn-crypto` и `rustvpn-proto` — чистая логика без async и ввода-вывода, поэтому их можно независимо покрывать модульными тестами и фаззить. `rustvpn-net` владеет компонентами, обращёнными к ОС. Бинарники — тонкие слои композиции.

## Плоскость управления

Демоны работают на Tokio:

- TCP-сессии и HTTP CONNECT-прокси — это задачи Tokio.
- Рукопожатия, открытие TAP, скрипты и статистика — работа плоскости управления.
- Допуск рукопожатий использует token bucket: 5/с на IP источника (всплеск 10) и 200/с глобально (всплеск 400); для TCP также применяется семафор параллелизма.
- Конфигурация хранится в `RwLock<ConfigSet>` и обновляется каждые 60 секунд; неудачный разбор сохраняет предыдущий набор.

У каждого UDP-peer'а есть задача декодирования, питаемая каналом mpsc; у TCP — задача чтения на каждое соединение. Это намеренно проще исходного предложения «один worker на ядро»: сохраняется корректность и ограниченность очередей, а дорогие части (пакетная обработка, SIMD, повторное использование буферов) обрабатываются внутри задач.

## Путь данных

### Отправка

1. Прочитать кадр из TAP.
2. Проверить предел полезной нагрузки для конкретного режима (`MTU-1`, `MTU-25` или `MTU-9`). Кадры превышающего размера отклоняются и учитываются в счётчиках, но никогда не усекаются.
3. Записать заполнитель `0x80`, при необходимости дополнить до MTU (noise/CPR).
4. Закодировать с помощью `Encoder::encode_into` в переиспользуемые буферы: serial → XTEA PRP → разбиение keystream Salsa20 → тег Poly1305.
5. Передать буфер на проводе общему пакетному отправителю UDP (`sendmmsg`, до 64 датаграмм на системный вызов) или записать его в TCP-поток.
6. Обновить атомарные счётчики и вернуть буфер в пул.

### Приём

1. `recvmmsg` возвращает до 64 датаграмм на системный вызов (или один TCP-кадр).
2. Декодировать с помощью `Decoder::decode_into` в переиспользуемые буферы `payload`/`scratch`; проверить MAC до принятия serial.
3. Обновить окно воспроизведения, удалить заполнение, проверить завершающие нули.
4. Записать Ethernet-кадр в TAP (асинхронная запись через io_uring или epoll).
5. Обновить статистику; дубликаты и старые serial учитываются и отбрасываются.

`encode_into`/`decode_into` поддерживают классический путь и путь noise на уровне нулевых выделений памяти на пакет; encless всё ещё выделяет память для преобразования AONT/CnW.

### Бэкенды ввода-вывода

- UDP: пакетная обработка `recvmmsg`/`sendmmsg`, один общий пакетный отправитель на сокет.
- TAP: io_uring с пробуждением через eventfd (без пробуждений в простое), с запасным вариантом на epoll. `GOVPN_IO_URING=0` принудительно включает запасной вариант.
- Окно воспроизведения: 257-битная битовая карта в стиле `[u64; 5]`, O(1), без хеширования, без выделений памяти.
- Rekey: клиент инициирует свежее рукопожатие после 4 GiB (`MAX_BYTES_PER_KEY = 1 << 32`) трафика на проводе.

### SIMD

Salsa20 имеет бэкенд AVX2 с диспетчеризацией во время выполнения в `rustvpn-crypto/src/salsa_simd.rs`, обрабатывающий восемь блоков (или восемь независимых keystream'ов CnW) за один вызов ядра. Скалярный путь RustCrypto является эталонным и дифференциально тестируется против пути AVX2. Поверхность `unsafe` ограничена этим модулем; весь остальной код использует безопасный Rust.

## Выбор криптографии

| Примитив | Реализация |
|---|---|
| Salsa20/XSalsa20 | RustCrypto `salsa20` + быстрый путь AVX2 |
| Poly1305 | RustCrypto `poly1305`, программный бэкенд закреплён через `.cargo/config.toml` |
| XTEA | в дереве проекта, совместим по байтам с Go |
| BLAKE2b-256 | RustCrypto `blake2` |
| Argon2d v1.3 | RustCrypto `argon2` (`m/t/p`, 32-байтный результат как seed для Ed25519) |
| Ed25519 | `ed25519-dalek` |
| X25519 + Elligator | `curve25519-dalek` + порт кодирования представителей `extra25519` из Go |
| Постоянное время | `subtle` для сравнений MAC/заполнения |

Закрепление программного бэкенда Poly1305 — измеренный выбор: на Zen3 бэкенд AVX2 этого крейта имеет большую фиксированную стоимость на сообщение и в несколько раз медленнее своего скалярного бэкенда на малых пакетах. Векторы Go подтверждают побайтовое равенство. См. [Производительность](performance.md).

## Инварианты протокола, покрытые тестами

- Рукопожатие: четыре длины сообщений (48/80/120/16), порядок полей, позиция заполнения, `IDtag` и результирующий master key.
- Транспорт: раскладка tag/ciphertext/nonce, смещения Salsa20, покрытие Poly1305, чётность/шаг serial и порядок байтов XTEA.
- Воспроизведение: семантика окна UDP и правила точного упорядочивания TCP.
- Encless: последовательность байтов AONT/CnW, расширение на 4128 байт, раскладка nonce XSalsa20, отклонение минимальной длины.
- Noise: длина заполнения и нулевое заполнение.
- Timesync: XOR метки времени с секундной гранулярностью в `IDtag`.
- Верификатор: формат строки, параметры Argon2d, вывод seed для Ed25519.
- Конфигурация: имена полей/значения по умолчанию, ограничение MTU, encless→noise, требование длинной формы верификатора.
- Скрипты: `GOVPN_IFACE`/`GOVPN_REMOTE`; сервер использует stdout скрипта `up`, когда `iface` пуст.
- Статистика: имена/типы полей JSON.
- Прокси: ответ CONNECT и передача необработанного TCP.

## Стратегия тестирования

- **Дифференциальные векторы.** `testdata/go_vectors.json` содержит байт-точные выходные данные реализации на Go для каждого примитива, режима транспорта, сообщения рукопожатия и формы верификатора. Тесты сравнивают оба направления.
- **Модульные тесты/тесты эквивалентности.** Keystream'ы AVX2 против скалярных, круговые преобразования CnW/AONT, свойства окна воспроизведения, эквивалентность `encode_into` удобному API, loopback `sendmmsg`/`recvmmsg` и круговой обмен через socketpair через цикл io_uring.
- **Матрица совместимости.** `{Go,Rust} × {client,server} × {UDP,TCP,
  proxy} × {plain,noise,encless}` с TAP и сетевыми пространствами имён, включая ICMP через туннель. Матрица зафиксирована в корневом README.
- **Фаззинг** (пока не подключён к CI) — естественный следующий шаг для разбора пакетов, состояния рукопожатия, фрейминга TCP, разбора YAML/верификатора и декодирования AONT/CnW; крейты с чистой логикой делают это простым.

## Отклонения и открытые вопросы

- Нет шардирования `SO_REUSEPORT` с потоком на ядро; один сокет на протокол с общим пакетным отправителем. Проще, а измеренный выигрыш дали пакетная обработка и SIMD, а не шардирование.
- Нет автоматической настройки эффективного MTU.
- Сборки для FreeBSD/macOS не тестировались.
- Путь encless всё ещё выделяет память; возможен кодировщик AONT/CnW с пулом буферов.
