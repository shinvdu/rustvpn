# Дизайн

[English](../en/design.md) | [中文](../zh/design.md) | **Русский**

Эта страница описывает реализованную архитектуру. Исходное предложение по дизайну сохранено в этом репозитории как [`docs/design.md`](../design.md) (написано до переименования, поэтому там ещё используются старые имена `govpn-*`); эта версия фиксирует то, что было действительно построено и почему.

## Цели

1. **Совместимость по проводному формату прежде всего.** Бинарники на Rust должны быть полноценной заменой GoVPN 5.7 (drop-in). Байты протокола, флаги CLI, значения по умолчанию, `peers.yaml`, скрипты, JSON статистики и поведение прокси — всё это часть поверхности совместимости.
2. **Вторая реализация как оракул.** Дифференциальное тестирование против кода на Go выявляет дрейф протокола, который одни только модульные тесты пропустили бы.
3. **Предсказуемый путь данных.** Никаких выделений памяти в куче на каждый пакет в установившемся режиме, ограниченные очереди, явное владение буферами и пакетный ввод-вывод.
4. **Операционный паритет.** Та же модель развёртывания, права доступа и диагностика, что и у демонов на Go.

Не-цели этой версии: протокол v2, клиенты для Windows/macOS, кроссплатформенный GUI клиента (Linux MVP уже есть, см. [`client-ui.md`](../client-ui.md); кроссплатформенный план — [`client-ui-plan.md`](../client-ui-plan.md)), управление маршрутизацией/NAT, управляющие плоскости балансировки нагрузки или изменение любого криптографического алгоритма (это нарушило бы совместимость). Серверный веб-интерфейс администратора реализован как отдельный процесс; см. «Плоскость администрирования» ниже.

## Структура воркспейса

```text
.
├── crates/rustvpn-crypto/   # primitives, AONT/CnW/encless, verifier, EGD
├── crates/rustvpn-proto/    # packet layout, codec, handshake state machines
├── crates/rustvpn-net/      # TAP, config, scripts, stats, peer lifecycle,
│                            # UDP batching, io_uring TAP
├── crates/rustvpn-control/  # admin↔server control protocol (Unix socket, JSON)
├── crates/rustvpn-admin/    # rustvpn-admind + rustvpn-admin-passwd (HTTP UI, SQLite)
├── crates/rustvpn-client/   # client binary
├── crates/rustvpn-server/   # server binary
├── crates/rustvpn-verifier/ # verifier binary
├── testdata/                # Go-generated differential vectors
└── docs/                    # this manual (en/zh/ru) + upstream design notes
```

`rustvpn-crypto` и `rustvpn-proto` — чистая логика без async и ввода-вывода, поэтому их можно независимо покрывать модульными тестами и фаззить. `rustvpn-net` владеет компонентами, обращёнными к ОС. Бинарники — тонкие слои композиции. `rustvpn-control` содержит только общие DTO и кодек кадров; крейты плоскости данных не зависят от зависимостей админки (axum, SQLite, статические ресурсы).

## Плоскость управления

Демоны работают на Tokio:

- TCP-сессии и HTTP CONNECT-прокси — это задачи Tokio.
- Рукопожатия, открытие TAP, скрипты и статистика — работа плоскости управления.
- Допуск рукопожатий использует token bucket: 5/с на IP источника (всплеск 10) и 200/с глобально (всплеск 400); для TCP также применяется семафор параллелизма.
- Конфигурация хранится в `RwLock<ConfigSet>` и обновляется каждые 60 секунд; неудачный разбор сохраняет предыдущий набор.

У каждого UDP-peer'а есть задача декодирования, питаемая каналом mpsc; у TCP — задача чтения на каждое соединение. Это намеренно проще исходного предложения «один worker на ядро»: сохраняется корректность и ограниченность очередей, а дорогие части (пакетная обработка, SIMD, повторное использование буферов) обрабатываются внутри задач.

## Плоскость администрирования (веб-UI)

Серверный веб-интерфейс администратора — **отдельная программа**, которая делит с плоскостью данных только библиотеки. `rustvpn-server` не линкует axum, SQLite или статические ресурсы и не останавливается при сбое админки.

```text
Браузер ──TLS──▶ Caddy/Nginx ──▶ rustvpn-admind
                                  ├─ HTTP API + встроенный статический UI (vanilla JS + Canvas)
                                  ├─ вход Argon2id / cookie сессии / CSRF / admin|viewer
                                  ├─ история SQLite, аудит, резервные копии конфигурации
                                  └─ проверка конфигурации и атомарная запись
                                           │
                                           │ /run/rustvpn/control.sock
                                           │ длина 4B BE + JSON, протокол v1
                                  rustvpn-server
                                  ├─ плоскость данных UDP/TCP/TAP
                                  └─ status/sessions/kick/reload/
                                     recent_sessions/validate_config/subscribe
```

### Протокол управления

- Только Unix domain socket, без TCP-слушателя. Включается через `-control PATH` (по умолчанию выключен).
- Кадр: 4-байтная длина в big-endian + JSON, предел 4 MiB. `hello` проверяет версию протокола и отклоняет несовместимого клиента без тихой деградации.
- Запросы: `hello`, `status`, `sessions`, `kick`, `reload`, `recent_sessions`, `validate_config`, `subscribe`.
- События: `session_started`, `session_ended` (с финальными счётчиками и причиной завершения), `config_reloaded`, `lagged`, `server_shutdown`. Сервер хранит последние 1024 события завершения для сверки при переподключении админки.
- Аутентификация: `SO_PEERCRED` разрешает root или группу сокета (`-control-group`; без неё — только пользователя сервера). Режим сокета `0660`/`0600`; не более 8 одновременных подключений.
- Команд `write_config`/`shutdown` нет: админка проверяет и пишет файл, жизненный цикл остаётся за systemd.

### Граница привилегий

| Процесс | Пользователь/группа | Возможности |
|---|---|---|
| `rustvpn-server` | `rustvpn`, группа `rustvpn-adm` | `CAP_NET_ADMIN`/`CAP_NET_RAW`; может запускать скрипты |
| `rustvpn-admind` | `rustvpn-admin`, основная группа `rustvpn-adm` | **без capabilities**; может писать каталог конфигурации и SQLite |
| Сокет управления | `rustvpn:rustvpn-adm` `0660` | только группа администрирования |
| Каталог конфигурации | `root:rustvpn-adm` `2770` | сервер читает; админка делает атомарный rename |
| Каталог скриптов | `root:root` `0755` | недоступен для записи группе администрирования |

При `-control` серверу **обязателен** хотя бы один `-script-dir`, иначе он отказывается запускаться. Каждый путь up/down должен находиться в белом списке, существовать, а каждый каталог от корня списка до родителя скрипта — принадлежать root/пользователю сервера и быть недоступным для записи группе и остальным. Сервер повторно проверяет это при загрузке конфигурации и перед каждым запуском скрипта. Админка может только указывать пути; редактировать или загружать содержимое скриптов она не может.

### Запись конфигурации

1. Отрисовать YAML и проверить тем же `ConfigSet`.
2. Вызвать `validate_config` сервера для проверки скриптов/путей.
3. Резервная копия → временный файл в том же каталоге → fsync → `rename`.
4. Вызвать `reload`; сервер применяет сразу.

Запись использует оптимистическую блокировку ETag. Когда сервер офлайн, предварительная проверка не проходит, и админка отказывается писать: конфигурация, резервные копии, история и аудит остаются доступными только для чтения. Так не остаётся полувалидной конфигурации, которую сервер отверг бы при следующем запуске.

### Учёт сессий

- Админка опрашивает активные сессии каждые 10 секунд для расчёта скоростей; события `session_started`/`session_ended` задают границы сессий.
- Счётчики из `session_started` служат базой первого замера; немедленно сработавший первый тик пропускается, а неизвестные сессии получают нулевую базу, чтобы трафик до сессии не попал в первый интервал.
- Сервер фиксирует финальные счётчики в `end_session()` и отправляет `session_ended`, поэтому последний интервал не теряется.
- При каждом запуске сервер генерирует случайный 52-битный `server_instance` как базу идентификаторов сессий. Это исключает коллизии первичных ключей SQLite после перезапуска и остаётся в пределах безопасных целых JavaScript.
- При перезапуске админка сначала получает `sessions` + `recent_sessions` и помечает как `server_restart` только те открытые записи, которые сервер уже не знает.

### Админка и UI клиента

- Аутентификация: пароли Argon2id, cookie сессии HttpOnly + SameSite=Strict, CSRF для операций записи, ограничение частоты входа; роли `admin`/`viewer`.
- Страницы: обзор, список/детали клиентов, графики трафика 1h/24h/7d/30d, история сессий, предпросмотр/применение/резервное копирование/восстановление конфигурации, аудит, живое обновление через SSE, Prometheus `/metrics` и проверки здоровья.
- По умолчанию слушает `127.0.0.1:8080`, доступ через SSH-туннель или TLS-обратный прокси; сокет управления не покидает хост.
- Хранилище: `/var/lib/rustvpn/admin.db` (SQLite WAL) хранит учётные записи, историю и аудит; `peers.yaml` остаётся единственным источником истины для конфигурации.
- **GUI клиента реализован как Linux MVP** ([`client-ui.md`](../client-ui.md)): статический UI на Tauri 2, непривилегированный GUI, демон `rustvpn-clientd` с минимальными привилегиями и общее ядро `rustvpn-client-core`. CLI и GUI остаются отдельными программами, которые делят только библиотеки. Windows/macOS и мобильные платформы не реализованы; главная сложность там — пользовательский Ethernet-шим на системах без L2, а не UI-фреймворк ([`client-ui-plan.md`](../client-ui-plan.md)).

## Путь данных

### Отправка

1. Прочитать кадр из TAP.
2. Проверить предел полезной нагрузки для конкретного режима (`MTU-1`, `MTU-25` или `MTU-9`). Кадры превышающего размера отклоняются и учитываются в счётчиках, но никогда не усекаются.
3. Записать заполнитель `0x80`, при необходимости дополнить до MTU (noise/CPR).
4. Закодировать с помощью `Encoder::encode_into` в переиспользуемые буферы: serial → XTEA PRP → разбиение keystream Salsa20 → тег Poly1305.
5. Передать буфер на проводе общему пакетному отправителю UDP (`sendmmsg`, до 64 датаграмм на системный вызов) или записать его в TCP-поток.
6. Обновить атомарные счётчики и вернуть буфер в пул.

### Приём

1. `recvmmsg` возвращает до 64 датаграмм на системный вызов (или один TCP-кадр).
2. Декодировать с помощью `Decoder::decode_into` в переиспользуемые буферы `payload`/`scratch`; проверить MAC до принятия serial.
3. Обновить окно воспроизведения, удалить заполнение, проверить завершающие нули.
4. Записать Ethernet-кадр в TAP (асинхронная запись через io_uring или epoll).
5. Обновить статистику; дубликаты и старые serial учитываются и отбрасываются.

`encode_into`/`decode_into` поддерживают классический путь и путь noise на уровне нулевых выделений памяти на пакет; encless всё ещё выделяет память для преобразования AONT/CnW.

### Бэкенды ввода-вывода

- UDP: пакетная обработка `recvmmsg`/`sendmmsg`, один общий пакетный отправитель на сокет.
- TAP: io_uring с пробуждением через eventfd (без пробуждений в простое), с запасным вариантом на epoll. `GOVPN_IO_URING=0` принудительно включает запасной вариант.
- Окно воспроизведения: 257-битная битовая карта в стиле `[u64; 5]`, O(1), без хеширования, без выделений памяти.
- Rekey: клиент инициирует свежее рукопожатие после 4 GiB (`MAX_BYTES_PER_KEY = 1 << 32`) трафика на проводе.

### SIMD

Salsa20 имеет бэкенд AVX2 с диспетчеризацией во время выполнения в `rustvpn-crypto/src/salsa_simd.rs`, обрабатывающий восемь блоков (или восемь независимых keystream'ов CnW) за один вызов ядра. Скалярный путь RustCrypto является эталонным и дифференциально тестируется против пути AVX2. Поверхность `unsafe` ограничена этим модулем; весь остальной код использует безопасный Rust.

## Выбор криптографии

| Примитив | Реализация |
|---|---|
| Salsa20/XSalsa20 | RustCrypto `salsa20` + быстрый путь AVX2 |
| Poly1305 | RustCrypto `poly1305`, программный бэкенд закреплён через `.cargo/config.toml` |
| XTEA | в дереве проекта, совместим по байтам с Go |
| BLAKE2b-256 | RustCrypto `blake2` |
| Argon2d v1.3 | RustCrypto `argon2` (`m/t/p`, 32-байтный результат как seed для Ed25519) |
| Ed25519 | `ed25519-dalek` |
| X25519 + Elligator | `curve25519-dalek` + порт кодирования представителей `extra25519` из Go |
| Постоянное время | `subtle` для сравнений MAC/заполнения |

Закрепление программного бэкенда Poly1305 — измеренный выбор: на Zen3 бэкенд AVX2 этого крейта имеет большую фиксированную стоимость на сообщение и в несколько раз медленнее своего скалярного бэкенда на малых пакетах. Векторы Go подтверждают побайтовое равенство. См. [Производительность](performance.md).

## Инварианты протокола, покрытые тестами

- Рукопожатие: четыре длины сообщений (48/80/120/16), порядок полей, позиция заполнения, `IDtag` и результирующий master key.
- Транспорт: раскладка tag/ciphertext/nonce, смещения Salsa20, покрытие Poly1305, чётность/шаг serial и порядок байтов XTEA.
- Воспроизведение: семантика окна UDP и правила точного упорядочивания TCP.
- Encless: последовательность байтов AONT/CnW, расширение на 4128 байт, раскладка nonce XSalsa20, отклонение минимальной длины.
- Noise: длина заполнения и нулевое заполнение.
- Timesync: XOR метки времени с секундной гранулярностью в `IDtag`.
- Верификатор: формат строки, параметры Argon2d, вывод seed для Ed25519.
- Конфигурация: имена полей/значения по умолчанию, ограничение MTU, encless→noise, требование длинной формы верификатора.
- Скрипты: `GOVPN_IFACE`/`GOVPN_REMOTE`; сервер использует stdout скрипта `up`, когда `iface` пуст.
- Статистика: имена/типы полей JSON.
- Прокси: ответ CONNECT и передача необработанного TCP.

## Стратегия тестирования

- **Дифференциальные векторы.** `testdata/go_vectors.json` содержит байт-точные выходные данные реализации на Go для каждого примитива, режима транспорта, сообщения рукопожатия и формы верификатора. Тесты сравнивают оба направления.
- **Модульные тесты/тесты эквивалентности.** Keystream'ы AVX2 против скалярных, круговые преобразования CnW/AONT, свойства окна воспроизведения, эквивалентность `encode_into` удобному API, loopback `sendmmsg`/`recvmmsg` и круговой обмен через socketpair через цикл io_uring.
- **Плоскость администрирования.** Кодек протокола управления и согласование версий, права сокета и `SO_PEERCRED`, белый список скриптов и повторная проверка перед запуском, предварительная проверка конфигурации, базы выборок и сверка «осиротевших» записей. Админка покрывается модульными тестами с поддельным управляющим сокетом; сквозные тесты используют netns + TAP для проверки кика, финальных счётчиков и сверки при переподключении.
- **Матрица совместимости.** `{Go,Rust} × {client,server} × {UDP,TCP,
  proxy} × {plain,noise,encless}` с TAP и сетевыми пространствами имён, включая ICMP через туннель. Матрица зафиксирована в корневом README.
- **Фаззинг** (пока не подключён к CI) — естественный следующий шаг для разбора пакетов, состояния рукопожатия, фрейминга TCP, разбора YAML/верификатора и декодирования AONT/CnW; крейты с чистой логикой делают это простым.

## Отклонения и открытые вопросы

- Нет шардирования `SO_REUSEPORT` с потоком на ядро; один сокет на протокол с общим пакетным отправителем. Проще, а измеренный выигрыш дали пакетная обработка и SIMD, а не шардирование.
- Нет автоматического согласования path MTU: в v1 используется двусторонний числовой MTU линии, IP MTU TAP-интерфейса выводится локально из режима, а `mtu: auto` отложен до v2.
- Сборки для FreeBSD/macOS не тестировались.
- Путь encless всё ещё выделяет память; возможен кодировщик AONT/CnW с пулом буферов.
- Поддерживается только один экземпляр админки (без блокировки процесса; два экземпляра будут делать выборки дважды); плоскость управления — локальный Unix socket, без управления с других хостов.
- В админке нет TOTP и автоматического отключения/ограничения скорости по квотам; при офлайн-сервере конфигурацию записать нельзя.
- GUI клиента пока только для Linux. Доступны пакеты deb/rpm, интерфейс и меню трея на zh/en/ru и опциональный подписанный Tauri updater; собственный ключ обновлений и сервис обновлений не поставляются, а rpm нужно собирать через `rpmbuild`. Туннелирование IPv6, Windows/macOS и мобильные платформы по-прежнему вне области работ (трей, single instance, автозапуск и keychain уже есть) ([`client-ui-plan.md`](../client-ui-plan.md)).

Далее: [Производительность](performance.md).
