# Protocol

**English** | [中文](../zh/protocol.md) | [Русский](../ru/protocol.md)

RustVPN implements the GoVPN 5.7 wire protocol byte for byte. This page
describes the pieces you need to understand the configuration and the
security properties. Where the old Go manual and the code disagreed, the
code wins; the Rust implementation is differentially tested against
vectors generated by the Go code.

## Cryptographic primitives

| Purpose | Algorithm |
|---|---|
| Key agreement | X25519 over `extra25519` / Elligator representatives |
| Authentication | Ed25519 (derived from the Argon2d verifier) |
| Hash | BLAKE2b-256 |
| Passphrase KDF | Argon2d v1.3, 32-byte output used as the Ed25519 seed |
| Stream cipher | Salsa20 (8-byte nonce) / XSalsa20 (24-byte nonce) |
| MAC | Poly1305 |
| Serial PRP | XTEA |
| Encoding (encless) | AONT + Chaffing-and-Winnowing |

## Identity and verifier

A client identity is a 128-bit, non-secret value. It is used as the XTEA
key for the handshake `IDtag` and as the Argon2 salt, and it appears in
the stats output. It is safe to transmit and store in the clear; the PRP
applied to it in handshake messages makes DPI/deanonymization harder.

A **verifier** is:

```
$argon2d$m=<KiB>,t=<iterations>,p=<parallelism>$base64(id)[$base64(pubkey)]
```

- Short form (client): identity only. The client derives the Ed25519 key
  from the passphrase and the identity.
- Long form (server): identity + Ed25519 public key. The server never sees
  the passphrase and cannot impersonate the client even if its file
  leaks.

Argon2d output (32 bytes) is used directly as the Ed25519 seed. Default
parameters are `m=4096`, `t=128`, `p=1`.

## Handshake (PAKE DH A-EKE)

Four messages establish a session. Each message ends with an **IDtag**:
the first 8 plaintext bytes XTEA-encrypted with the client identity as
the key (and XORed with the rounded timestamp when `timesync` is enabled).
The server uses it to find the peer; it also marks the packet as a
handshake.

Preparation:

1. The client has its identity, passphrase and the server's verifier
   public key (`DSAPub`).
2. It derives `DSAPriv`/`DSAPub`, generates a DH keypair
   `CDHPub`/`CDHPriv`, and a 64-bit nonce `R`.
3. `El()` is the Elligator representative encoding; `enc(k, n, m)` is
   Salsa20/XSalsa20 encryption with key `k` and nonce `n`.

```text
1. Client → Server   48 bytes
   R || enc(H(DSAPub), R, El(CDHPub)) || IDtag

2. Server → Client   80 bytes
   enc(H(DSAPub), R+1, El(SDHPub)) || enc(K, R, RS || SS) || IDtag

3. Client → Server  120 bytes
   enc(K, R+1, RS || RC || SC || Sign(DSAPriv, K)) || IDtag

4. Server → Client   16 bytes
   enc(K, R+2, RC) || IDtag
```

- The server learns the client address, decodes `CDHPub`, generates
  `SDHPriv`/`SDHPub`, computes `K = H(DH(SDHPriv, CDHPub))`, and sends a
  64-bit `RS` plus a 256-bit pre-master secret `SS`.
- The client computes `K`, recovers `SS`, generates `RC` and a 256-bit
  `SC`, and signs `K` with its Ed25519 key.
- The server verifies the signature with the verifier's public key,
  compares `RS`, and derives the session key
  **`MasterKey = SS XOR SC`**.
- The client confirms `RC`; both sides now share `MasterKey`.

`MasterKey` is high-entropy 256-bit. `K` is DH-derived and has at most a
128-bit security margin, so it is used only during the handshake. The
`R*` values provide handshake randomization and two-way authentication.

With **noise**, handshake messages are padded to fill the MTU. With
**encless**, each `enc()` is replaced by AONT + chaffing over the padded
data.

## Transport

```text
PACKET = TAG || CIPHERTEXT || NONCE

NONCE      = XTEA(PRP_KEY, SERIAL)
CIPHERTEXT = Salsa20(KEY, NONCE, DATA || PAD(0x80) || ZEROS)
TAG        = Poly1305(AUTH_KEY, CIPHERTEXT || NONCE)
```

- `SERIAL` is the packet sequence number: odd for client→server, even for
  server→client, incremented by 2. Client and server start at 0 and 1 and
  expect 2 and 3 respectively.
- `PRP_KEY` is the first 128 bits of the Salsa20 keystream with the
  session key and a zero nonce. `SERIAL` is kept in plaintext internally
  but transmitted only as the XTEA-encrypted `NONCE`.
- `ENCRYPT` uses the established session key and the encrypted serial as
  the Salsa20 nonce. The first 32 bytes of keystream are the Poly1305
  one-time key, the next 32 bytes are discarded, and payload encryption
  starts at byte 64.
- `DATA` is the Ethernet frame. `PAD` is a single `0x80` byte; optional
  zero bytes follow to fill the packet to the MTU (noise/CPR).
- Duplicate or too-old serials are dropped by a **257-bit sliding replay
  window**.

## Noise

Noise pads every outgoing packet to the configured MTU. It hides payload
lengths and is required for the intended effect of CPR; enable it on both
sides. It is off by default and can markedly increase traffic. See
[MTU](configuration.md#mtu) for the payload cost.

## Encless

Encryptionless mode replaces stream encryption with confidentiality-
preserving **encoding**:

```text
PACKET  = ENCODED || NONCE
ENCODED = Chaff(AONT(DATA || PAD || ZEROS))
NONCE   = XTEA(PRP_KEY, SERIAL)
```

- AONT (All-Or-Nothing Transformation) is a keyless transform: decoding
  any part requires the whole encoded value.
- Chaffing-and-Winnowing uses only Poly1305 (an authentication primitive)
  to encode bits as pairs of candidate MACs. There is no encryption
  function and no separate explicit MAC.
- Every packet grows by **4128 bytes** (32-byte AONT header + 4096 bytes
  of chaff), so this mode is expensive.
- It forces noise. The client supports it only over TCP, matching GoVPN;
  the server must be listening on TCP (or `all`).

Why it exists: some jurisdictions can compel disclosure of encryption keys
but not authentication/signing keys, and some forbid encryption outright.
Encless keeps confidentiality using only signing/MAC primitives. Its name
is about the mechanisms, not the result: transmitted data is still
confidential and authentic.

## Network transport

UDP is the default and is recommended: it is lighter and avoids the
"TCP meltdown" pathology (reliable-over-reliable head-of-line blocking).
TCP exists for environments where only TCP is allowed. `-proto all` on the
server listens on both.

## HTTP proxy

On the wire the proxy is just TCP. The server's `-proxy` listener replies
`HTTP/1.0 200 OK` to any request and enters the TCP session state machine;
the client sends `CONNECT host:port` and optionally `Proxy-Authorization`.
Handshake and transport bytes are identical to a direct TCP connection.

## Compatibility notes

The following are intentionally identical to GoVPN 5.7 and are covered by
byte-exact vectors:

- handshake message sizes, field order, padding position and `IDtag`;
- Salsa20 offsets (auth key, discarded bytes, payload start);
- serial parity, step, initial/expected values and XTEA byte order;
- the replay-window semantics;
- encless expansion and XSalsa20 nonce layout;
- verifier string syntax, Argon2d parameters and Ed25519 seed derivation;
- `GOVPN_IFACE` / `GOVPN_REMOTE` script variables and stats JSON names.
